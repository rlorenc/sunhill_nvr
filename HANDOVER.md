## 0.3.16 - zgodność archiwum HEVC

Baza `33a37d8` (0.3.15). Administrator zgłosił błąd odtwarzania najnowszych segmentów mimo HTTP 200: nagrania 30576 i 30563 zawierają HEVC `hev1` i AAC `mp4a`, natomiast live działa. `recorder.py` i `supervisor.py`: równoległy, ograniczony do 5 s na kamerę odczyt kodeka aliasu głównego przed uruchomieniem procesu (maks. 8 równoległych prób); tylko rozpoznane HEVC otrzymuje filtr bitstream i tag `hvc1` bez kodowania obrazu. Brak wyniku nie blokuje zapisu, a wczesny błąd wymusza próbę bez tagu, zachowując dotychczasową awaryjną konwersję dźwięku do AAC. Nie zmienia się go2rtc ani konfiguracja kamery. Nierozpoznany strumień lub awaryjny zapis może nadal dać `hev1`.

`archive_compat.py`, `web.py`, `files.py`, `static/app.js`, `workers.py`: po błędzie źródła/dekodowania i rozpoznaniu niezgodnego tagu HEVC archiwum pojedynczej kamery ponawia odtwarzanie tego samego nagrania i pozycji przez uwierzytelnione `/file?compat=hvc1`; tryb zapamiętany dla kamery do przeładowania strony. MP4 z innym kodekiem lub już `hvc1` przechodzi bez modyfikacji. Remux z kopią obrazu i dźwięku, filtr HEVC i weryfikacja tagu oraz długości; plik oryginalny pozostaje nietknięty i jest nadal pobierany przez `download=1`. Pamięć podręczna poza archiwum w `.archive-hvc1-cache` przy bazie SQLite, klucz tożsamości pliku, maks. 1 GiB źródła, 2 GiB wyników i 128 wpisów, co najmniej 512 MiB rezerwy przed remux, pojedyncza równoległa konwersja z limitem 20 s FFmpeg. Wpisy wygasają po godzinie bez użycia, czyszczenie przy żądaniu i cyklu health, aktywne deskryptory chronione przed usunięciem. Zakresy HTTP dotyczą tej samej kopii, zachowane uprawnienia i blokada oryginału. W razie braku możliwości przygotowania pliku nadal działa diagnostyka i dotychczasowy fallback. Nie wprowadzono transkodowania HEVC do H.264 ani zmiany funkcji synchronizowanego archiwum wielu kamer; przeglądarka musi obsługiwać HEVC. Standardowa aktualizacja, bez repair i bez refresh-recovery, nie zmienia ścieżek, indeksu ani schematu bazy.

Weryfikacja lokalna: API 106/106 (rzeczywisty remux HEVC, HEAD, Range, autoryzacja i oryginalny download); archive_compat 4/4 (rzeczywiste MP4 HEVC/AAC, identyczne zdekodowane klatki w porównaniu, tag nowego segmentu, cache i wygaśnięcie, H.264 bez zmian, fallback supervisora); supervisor 21/21, recorder 16/16, workers 20/20, files 8/8, CLI 17/17, media 11/11, pakowanie 10/10. JS DOM i Chromium: odtwarzanie i przejścia realnych syntetycznych H.264 MP4, symulacja odrzucenia `hev1` i zaakceptowania źródła zgodności oraz przejście do wcześniejszego segmentu przy niepowodzeniu. Safari i fizyczne pliki 30576/30563 nie były dostępne do testu; działanie produkcyjne poprzednich wersji pozostaje potwierdzone. Formalny gate CI Ubuntu nie był uruchomiony. ## Wznowienie w nowym środowisku

Po rozpakowaniu można odtworzyć Git poleceniem `git clone -b main sunhill-nvr-history.bundle sunhill-nvr-repo`. Pracować w klonie, odczytać AGENTS.md i dokumenty projektowe, sprawdzić HEAD oraz status. Przykładowe polecenia lokalne z katalogu repozytorium:

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -v
node tests/browser_smoke.js
```

Testy instalacji i integracji wymagają osobnej jednorazowej VM; patrz `.github/workflows/ubuntu.yml`, `docs/instalacja-testowa.md` i `tests/ubuntu_install_smoke.sh`. Nie uruchamiać instalatora na środowisku z rzeczywistymi nagraniami.
